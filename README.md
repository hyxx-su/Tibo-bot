# Tibo-bot

Tibo(`@thsottiaux`)의 새 X 게시글·답글을 Discord로 보내는 Cloudflare Workers 봇입니다. **1분마다 자동 확인하며 맥북을 켜둘 필요가 없습니다.** 미러의 갱신 지연이 있으므로 X 게시 후 1분 이내 도착을 보장하는 것은 아닙니다.

## 동작

1. 처음에는 현재 최신 글을 기준점으로 저장합니다. 과거 글을 한꺼번에 보내지 않습니다.
2. 이후 발견한 일반 게시글·답글은 **제목 링크·한국어 요약 목록·X 원문 링크**를 보냅니다. 본문 없이 이미지·GIF·동영상만 첨부한 답글도 포함합니다. 모든 신규 글을 먼저 분석하며, 링크 미리보기는 허용하고 멘션은 끕니다.
3. 수집한 모든 신규 글·답글을 키워드 유무와 관계없이 Gemini 3.5 Flash-Lite로 분석합니다. 같은 작성자의 스레드·인용 글과 인용 ID에 연결된 저장 문맥을 함께 읽습니다. 자동 알림 전용 분석 경로를 사용합니다.
4. 초기화로 판단된 글은 **경고 제목·상태별 제목 링크·요약·원문 링크를 한 메시지로** 보냅니다. 링크만 따로 먼저 보내지 않습니다. 예정·진행 중·전체 반영 완료·단순 언급을 구분합니다. “Rest and reset” 단독은 휴식 표현일 수 있지만, 같은 작성자가 같은 스레드에 초기화 기한을 덧붙인 경우 문맥을 함께 읽습니다.
5. 원문에 근거가 있는 시각은 **한국시간(KST)** 으로 표시합니다. 날짜·시간대가 불명확하면 확정할 수 없다고 표시합니다.

게시 시각이 `2026-10-25 12:00 UTC`이고 원문이 `tomorrow at 9am PT`라면 한국시간은 **2026-10-27 01:00**입니다. `in 2 hours`는 해당 게시 시각 기준으로 계산합니다. `By midnight PST`는 그 표현을 게시한 당시 PST 날짜의 다음 자정을 기한으로 계산합니다. 예를 들어 10월 25일 03:40 UTC의 해당 답글은 **10월 25일 17:00 KST까지**입니다. 원문의 PST는 UTC−8로 유지하며 PT(서머타임 적용 지역 시각)로 임의 교체하지 않습니다. 서머타임은 지역 시간대를 통해 반영하며, 전환 시점의 중복·존재하지 않는 시각은 확정하지 않습니다.

`GATEWAY_ENABLED="true"`이면 Cloudflare Durable Object 한 개가 Discord Gateway 연결을 유지하여 멤버 목록에 **온라인**으로 표시합니다. 맥북을 켜둘 필요가 없습니다. 연결이 끊기면 기존 Cron이 재접속을 시도하며, 알림 수집·발송은 별도 경로로 계속 실행됩니다.

## X 게시글 알림 예시

일반 글은 제목 링크·한국어 요약 목록·원문 링크 순서로 보냅니다. 제목과 핵심 요약 배열은 기존 Gemini 분류 호출에서 함께 생성하므로 별도 모델 호출을 추가하지 않습니다. 정보가 충분한 일반 글은 2~4개, 초기화 관련 글은 2~3개의 항목을 중요도순으로 표시하며 짧은 글은 1개만 사용합니다. 같은 사실을 반복하거나 원문에 없는 원인·영향·일정으로 항목 수를 채우지 않도록 지시합니다. 항목은 최대 4개·각 180자로 검사하고 같은 문장을 중복 제거합니다. 기존 한 문장 분석도 호환합니다. 구조 검증은 사실 정확성 보장이 아니며 요약이 길어지면 출력 토큰·응답 시간이 증가할 수 있습니다.

```md
**[에디터의 새로운 색상 테마](<https://x.com/thsottiaux/status/POST_ID>)**
- 새로운 색상 테마를 웹과 데스크톱에 출시했습니다.
- 팀 관리자는 설정에서 해당 테마를 비활성화할 수 있습니다.
https://x.com/thsottiaux/status/POST_ID
```

초기화 관련 글은 맨 위에 경고 제목을 붙입니다. 예정·진행·완료·단순 언급과 저장형 지급을 구분한 제목을 사용하며 완료 글도 이 텍스트 형식으로 보냅니다.

```md
**## :warning: 초기화 관련 내용 감지 :warning:**
**[저장형 리셋 지급 진행 중](<https://x.com/thsottiaux/status/POST_ID>)**
- 모든 유료 계정에 저장형 초기화권을 불러오는 중이라고 안내합니다.
https://x.com/thsottiaux/status/POST_ID
```

제목과 하단 링크는 수집한 현재 글의 동일한 ID로 만듭니다. 제목 링크는 미리보기를 억제하고 하단 링크는 허용합니다. 직접 만든 원문 카드는 추가하지 않으며, 사진·GIF를 포함한 자동 미리보기 생성은 Discord와 X 응답에 따라 달라집니다. 모델이 만든 외부 링크와 Discord 서식은 제거·이스케이프하고 멘션은 비활성화합니다.

유효한 예정 시각이 있는 scheduled 알림에는 요약 다음에 `# 예정 시각: 10월 25일 17:00까지`와 `-# 한국시간(KST) · 원문 분석`을 표시합니다. 시각 미정이면 두 줄 모두 생략하며, 게시 시각·과거 예고를 현재 예정 시각으로 표시하지 않습니다. `within the next 2 hours`는 게시 시각부터 2시간 이내라는 기한으로 계산하고, `EOD` 같은 모호한 표현은 자정으로 바꾸지 않습니다.

본문이 비어 있는 이미지·GIF 글도 수집합니다. 이미지 내용을 보았다고 가정하지 않고 `이미지·미디어 게시글` 제목과 첨부 사실만 표시합니다. 분석 최종 실패 또는 기존 저장 분석에 요약이 없으면 원문 링크만 보내 내용을 지어내지 않습니다.

`reset_type`(regular/banked/unknown)과 상태는 독립적입니다. regular는 현재 사용량 초기화, banked는 나중에 사용할 초기화권 지급이며 ‘정기’라는 유형명이 고정 주기를 보장하지 않습니다. 유형은 원문 근거로 확인하고 unknown을 regular로 채우지 않습니다. 관련 언급과 진행을 완료로 확대하지 않습니다.

X 알림의 새 형식은 일반 문자열로 저장합니다. 별도 사이트 감시의 초록색 임베드와 기존 v1/v2 대기열 호환성은 유지하며 과거 글·발송 이력을 초기화하지 않습니다.

예고를 인용한 `It is all propagated`와 같은 후속 글은 Gemini가 새 글 자체의 근거로 완료 여부를 판별합니다. `still propagating` 등 진행 중인 안내는 완료 메시지로 보내지 않습니다. 인용 글이 다른 작성자의 것이거나 무관한 배포·질문·부정이면 이전 초기화 예고로 연결하지 않습니다.

[Codex Resets의 과거 공지 기록](https://codex-resets.com/)에서 키워드 없는 짧은 완료 안내와 초기화권 지급 사례를 확인해 판별 지침을 보완했습니다. 사이트의 외부 판정으로 Gemini의 원문 분석 정답을 덮어쓰지는 않습니다. 별도 사이트 알림은 아래와 같이 출처를 명시해 전달합니다. 짧은 완료 답변은 실제 연결 문맥이 초기화를 가리킬 때만 사용합니다. 다른 기능의 배포 완료와 단순 초기화 선언만으로 사용량 전체 반영 완료를 확정하지 않습니다. 실행 상태·기한이 불명확한 선언은 관련 안내로, 연결된 후속 글에 미래 기한이 있으면 예정 안내로 구분합니다. 나중에 직접 사용하는 초기화권(`banked reset`)은 지급 예정·진행·완료를 별도로 분류하며, 현재 사용량의 초기화 완료로 알리지 않습니다.

실제 게시글과 [codex-reset.com](https://codex-reset.com/)의 별도 참고 자료를 이용하는 [분석 평가 절차](docs/reset-evaluation.md)를 제공합니다. 모델을 별도로 학습시키는 대신, 정답이 정해진 사례와 독립 평가를 통해 프롬프트·원문 근거·시간 변환을 개선합니다. 수집 원본과 키는 공개 저장소에 포함하지 않습니다.

## 사이트 리셋 기록 알림

`WATCH_ENABLED="true"`와 `SITE_RESETS_ENABLED="true"`이면 [codex-resets.com 공개 API](https://codex-resets.com/api/docs)의 실행된 리셋 목록을 기존 1분 Cron에서 별도로 확인합니다. Gemini를 호출하지 않으며 예정 기록·관찰 대기·예측 확률은 완료 알림으로 보내지 않습니다. `codex-reset.com`은 평가 참고 자료로만 사용하며 자동 대체 수집원으로 사용하지 않습니다.

사이트에서 새 기록을 발견하면 `/채널`로 설정한 채널에 본문 없이 초록색 임베드 하나를 보냅니다.

```text
🔄 Codex 사용량 리셋 감지
유형: 정기 리셋 (regular) 또는 저장형 리셋 (banked)
발표 시각: YYYY-MM-DD HH:mm KST
출처: https://codex-resets.com/
원문: https://x.com/thsottiaux/status/POST_ID
```

발표 시각은 사이트의 `announced_at`을 KST로 바꾼 값이며, 사이트가 반영을 처음 관찰한 시각일 수도 있습니다. Tibo의 게시 시각이나 모든 계정의 실제 반영 시각과 같다는 뜻은 아닙니다. banked는 저장형 초기화권 지급이며 현재 사용량을 즉시 초기화했다는 의미가 아닙니다. 사이트가 원문 링크를 제공하지 않으면 `원문: 제공되지 않음`으로 표시합니다.

첫 정상 수집은 기존 기록을 기준점으로만 저장합니다. 그 이후 새로 발견한 기록부터 발송하며, 서버별 발송 이력과 유형·원문 ID로 반복 전송을 억제합니다. 같은 원문의 사이트 ID나 시각만 바뀐 경우 재전송하지 않습니다. X 게시글 알림과 사이트 확인 알림은 의도적으로 별개이므로 같은 원문 링크가 두 경로에서 각각 도착할 수 있습니다. 사이트 기록을 일반 채팅 답변이나 X 분류 결과에 주입하지 않습니다.

한 번에 최대 3페이지·300개를 검증합니다. 목록이 비었거나 페이지가 불완전하거나 형식·유형·시각이 잘못되면 기준점을 변경하지 않고 다음 주기에 다시 시도합니다. 429의 `Retry-After`를 반영하고 사이트 장애 중에도 이미 저장된 전송 작업은 복구합니다. 갱신 지연과 외부 장애 때문에 1분 이내 도착이나 누락 없는 수집을 보장하지 않습니다. 현재 `/상태`의 최근 확인 시각은 기존 X 수집 기준이며 사이트 수집 상태는 운영 DB의 `site_reset_state`에서 확인합니다.

활성화 전 `0004_site_resets.sql`을 적용해야 합니다. `SITE_RESETS_ENABLED="false"`로 배포하면 사이트 수집·발송을 중지하고 대기 기록은 보존합니다. 기존 X 알림은 계속됩니다. 다시 켤 때 기준점이나 이력을 지우지 마세요.

## 서버 입장과 알림 채널 설정

봇이 서버에 입장하면 아래 안내와 채널 선택 메뉴를 보냅니다.

> 반가워요! 저는 Tibo봇이에요.
>
> Tibo의 새 글과 초기화 안내를 받을 채널을 선택해 주세요.

서버 관리 권한(또는 관리자 권한)이 있는 사용자가 메뉴에서 텍스트·공지 채널 하나를 선택합니다. `/채널`으로 메뉴를 다시 열거나 `/채널 채널:#원하는채널`로 바로 지정할 수 있습니다. 봇의 채널 보기·메시지 보내기·링크 임베드 권한을 확인한 후 저장하며, 권한이 부족하면 기존 설정을 유지합니다. 설정 결과는 사용자에게 비공개로 알려주며, 선택한 채널에도 `✅ 알림 채널 설정 완료` 임베드와 “이제부터 이 채널에서 Tibo의 새 글과 초기화 안내를 보내드릴게요.”라는 공개 안내를 보냅니다. 동일 설정 요청의 재시도에는 같은 Discord nonce를 사용합니다. 설정 저장 후 안내 전송만 실패하면 저장된 채널은 유지하고 실패 사실을 구분해 알려줍니다.

- 환영 안내는 봇이 전송할 수 있는 시스템 채널, 없으면 텍스트·공지 채널 중 하나에 보냅니다. 쓸 수 있는 채널이 없으면 `/채널`을 사용하세요.
- 재연결 때 같은 서버에 환영 안내를 반복하지 않습니다. 기존에 설치된 서버에도 첫 기능 적용 시 한 번 안내합니다.
- 새 서버는 채널을 선택한 이후 발견한 글부터 받습니다. 과거 글은 한꺼번에 보내지 않습니다. 기존 운영 서버는 배포 설정의 알림 채널을 최초 한 번 가져와 유지합니다.
- 서버별 채널과 발송 결과를 따로 저장합니다. 한 서버의 전송 실패는 다른 서버를 중단시키지 않으며, Gemini 분석은 게시글당 공통으로 처리합니다.
- 채널 변경 뒤 이미 이전 채널로 발송 대기하던 메시지는 취소합니다. 새로 처리하는 메시지는 선택한 채널로 보냅니다.
- 알림 채널이 삭제되면 해당 설정을 해제하고 알림을 일시 중지합니다. 봇이 전송할 수 있는 시스템 채널, 없으면 다른 텍스트·공지 채널에 **알림 채널을 다시 선택해 주세요** 임베드와 선택 메뉴를 한 번 보냅니다. 안내가 온 채널이 자동으로 알림 채널로 설정되는 것은 아닙니다.
- 서버 관리자는 안내 메뉴나 `/채널`으로 다시 선택할 수 있습니다. 선택 이후 발견한 글부터 새 채널로 보내며, 삭제된 채널로 대기·실패했던 알림은 취소합니다. 성공한 발송 이력과 다른 서버의 설정은 보존합니다.
- 재연결 때 기존 목적지를 확인하고, 전송 시 Discord가 명시적으로 `Unknown Channel`을 반환한 경우도 복구합니다. 단순 권한 오류나 일시적인 API 장애만으로 채널 설정을 해제하지 않습니다. 안내를 보낼 채널이 없으면 미설정을 유지하고 10분 뒤 다시 확인합니다.
- 삭제 이벤트는 Gateway에서 처리하고 미완료 안내의 정기 복구 확인은 1분마다 실행합니다. 실제 메시지 도착은 Queue 대기와 외부 API 응답에 따라 늦어질 수 있으며 삭제 즉시 도착을 보장하지 않습니다.
- 봇이 서버에서 나가면 해당 서버 알림을 비활성화합니다. 다시 입장하면 채널을 다시 선택합니다.

## 명령

| 명령 | 동작 |
| --- | --- |
| `/채널 [채널]` | 서버 관리자용 채널 선택 메뉴 또는 지정한 채널로 변경 |
| `/상태` | 알림 작동 여부·알림 채널·최근 확인 시각을 비공개 임베드로 표시 |

`/채널`과 `/상태`는 봇이 설치된 서버에서 사용합니다. 테스트용 `/검증`은 운영 전환에 따라 제거했습니다. `/상태`는 본인에게만 현재 서버의 알림 작동 여부·채널·최근 확인 시각을 표시합니다.

`/상태`는 작동 여부를 제목으로 표시하고 알림 채널·최근 확인 시각만 담은 임베드 하나로 제공합니다. 한국시간 절대 시각과 Discord 상대 시간 태그를 함께 표시하며, 건수와 감시 기준점 등 내부 처리 정보는 노출하지 않습니다. 정상은 초록색, 확인 중·지연·미설정은 노란색, 오류는 빨간색이며 문제가 있을 때만 사용자에게 필요한 안내를 추가합니다. 첫 수집 전·채널 미설정·연결 확인 중·최근 성공이 3분 넘게 오래된 경우는 정상으로 표시하지 않습니다. 수집 오류와 처리·전송 실패는 내부 판정에 계속 사용합니다. 결과는 실행한 사용자에게만 보입니다.

## 일반 채팅으로 초기화 질문

`RESET_CHAT_ENABLED="true"`인 봇을 `Tibo야 초기화있니?`, `티보야 리셋 있어?`, `@Tibo 오늘 초기화 언제야?`처럼 직접 부르면 한국어 한 줄로 답장합니다. 서버에서 봇이 볼 수 있고 메시지를 보낼 수 있는 채널에서 사용할 수 있습니다.

- 예정: `있지. 오늘 17:00(KST)까지 초기화 예정이야.`
- 오늘 완료 공지가 있음: `오늘 초기화는 이미 끝났다는 공지가 있어. 달려보자.`
- 오늘 공지를 확인하지 못함: `아직 오늘 초기화 소식은 못 봤어.` 등 200개 문구

기존에 저장한 Gemini 분석을 읽으며 질문마다 모델을 호출하지 않습니다. 인사·관련 없는 질문·개인 계정 안내는 서버 활성 여부만 조회하고 게시글 분석 조회를 생략합니다. 최근 100개 수집 글 중 7일 이내의 최신 관련 공지를 사용합니다. 진행 중·시각 미정·기한 경과·수집 장애·분석 대기는 별도로 답하며, 공지가 없다는 이유로 오늘 초기화가 없다고 단정하지 않습니다. 답변 말투는 정해진 짧은 한국어 문구이며 Tibo 본인의 발언을 생성하는 기능은 아닙니다.

`초기화 없지?`, `언제쯤 해?`, `몇 시간 남았어?`, `벌써 끝났어?`처럼 표현과 띄어쓰기가 달라도 인식합니다. 오늘·내일·모레·어제를 구분합니다. 인사나 해석하지 못한 질문에는 `초기화 관련 질문에만 답변할 수 있어. 초기화 일정이나 진행 상태가 궁금하면 물어봐!`라는 안내만 보내며 재질문 문구는 붙이지 않습니다. 직접 초기화를 실행하거나 개인 계정의 사용량을 조회할 수는 없습니다. 한국어 전체를 이해하는 범용 대화 모델은 아니며 지원하는 주제·질문 표현으로 판별합니다.

`초기화 줘라`, `리셋 해주셈`, `한도 좀 풀어줘`, `초기화 제발`, `리셋 ㄱㄱ` 같은 부탁·요구에도 짧게 반응한 뒤 확인된 초기화 일정·진행 상태를 답합니다. 기능·권한 설명으로 답변을 대신하지 않습니다. 봇이 직접 초기화를 실행하거나 요청을 처리했다고 말하지 않습니다. `초기화 언제 해줘?`·`날짜 좀`은 일정 질문, `초기화 안 해?`는 상태 질문, `리셋 함?`·`다 됨?`은 완료 질문으로 구분합니다. 관련 언급은 있지만 시간이 미정인 상태에는 짧은 문구 20개를 섞습니다. 같은 채널의 최근 5개 선택과 동일한 문구를 피하며, 기존 선택 번호를 사용하므로 재시도마다 다시 추첨하지 않습니다.

검토한 질문 200개는 `test/fixtures/reset-questions.mjs`에 기대 의도와 함께 보관합니다. 부탁형은 짧은 반응 뒤 실제 상태를 답하며, 출처 요청에는 저장된 최신 관련 글의 게시 시각·분류·원문 링크를 표시합니다. 지난 완료 문의는 최근 100개 글 중 7일 이내의 완료 공지에서 찾고 조회 범위를 표시합니다.

개인 계정·적용 대상·한도 종류·취소·연기·이전 답변과의 비교는 저장된 분석만으로 확정하지 않습니다. `아직?` 같은 단편 질문과 복합 날짜는 구체화를 요청합니다. 주간·요일별 전체 일정 조회, 대화 기억, 원문 전체의 즉석 해석은 지원하지 않습니다. PST·PDT의 명시적인 정각은 KST로 계산하되 실제 초기화 일정과 구분합니다. 날짜 없는 PT, 분 단위·복수 시간대 등 지원하지 않는 시간 표현은 임의로 계산하지 않습니다. 질문마다 AI 호출이나 대화 원문 저장을 추가하지 않습니다.

오늘 초기화 공지를 확인하지 못한 경우에는 검토한 200개 문구에서 무작위로 선택합니다. 최근 10분 동안 같은 서버·채널의 질문에서 선택했던 문구 중 마지막 20개를 피합니다. 선택 번호는 작업에 고정하여 전송 재시도마다 문장이 바뀌지 않게 합니다. 다른 날짜의 질문, 예정·진행·완료·장애 안내에는 오늘 공지 미확인용 문구를 섞지 않습니다.

같은 서버·채널에서 **같은 사용자가 같은 문장을 5분 안에 두 번째로 보낼 때만** 현재 공지를 조회해 답한 뒤 `아까도 물어봤지? 😏`를 붙입니다. 세 번째부터는 답변만 보내며 다른 후속 문구는 붙이지 않습니다. 같은 사용자가 표현을 바꾸거나 다른 사용자가 같은 문장을 보내면 붙이지 않습니다. 호칭을 포함한 전체 문장의 SHA-256 해시를 비교하며, 유니코드 조합만 NFC로 통일하고 띄어쓰기·문장부호·대소문자 차이는 유지합니다. 이전에 답한 사이 새 완료 공지가 들어오면 최신 내용으로 답합니다. 질문 본문은 저장하거나 모델로 전송하지 않습니다. 재질문 판단에 쓰는 식별자·해시·시각과 답변 선택 번호는 10분 안의 기록만 다음 호출에서 유지합니다. 이전 버전의 해시 없는 기록은 동일 문장 판정에 포함하지 않습니다.

봇·웹후크·DM과 봇을 부르지 않은 문장은 무시합니다. 수신 시점부터 2분을 넘긴 작업은 답하지 않습니다. 동일 메시지 ID는 한 번만 처리하며 새 메시지로 다시 물으면 답합니다. 과다 호출은 사용자당 10초에 8회·채널당 10초에 30회·봇 전체 10분에 500회·UTC 날짜 기준 하루 1,000회로 제한합니다. 이 한도는 Gemini 자동 게시글 분석 100회와 별개이며 제한된 질문에는 응답하지 않습니다.

질문은 Gateway에서 받아 호출 제한 확인 후 바로 DB 조회·Discord 전송을 수행합니다. 정상 응답은 수집 Queue와 1분 수집 주기를 기다리지 않으며, 일시 실패만 기존 Queue에서 최대 2회 재시도합니다. 같은 nonce로 중복 전송을 억제합니다. `reset-question-replied` 로그의 `dispatchAgeMs`와 `processingMs`로 처리 시작 전 대기와 실제 처리 시간을 나눠 확인합니다. 연결 복구나 외부 API 응답 시간에 따라 실제 속도는 달라집니다.

수집, 분류, 발송은 Queue 단계로 처리합니다. 모든 신규 글을 분석한 뒤 결과에 따라 초기화 경고가 있는 요약 또는 일반 요약 중 하나만 보냅니다. 일반 글도 분석 지연이 발생할 수 있습니다. 분석이 최대 재시도 후 실패하면 링크만 전송합니다. D1의 미완료 작업은 다음 수집 주기에 재개합니다.

반복 수집에서는 페이지의 글 ID를 한 번에 조회하고 아직 저장하지 않은 글만 저장합니다. 미러에 늦게 나타나는 글을 놓치지 않도록 최고 ID가 아닌 실제 저장 여부로 확인하며, 동시 저장 충돌에는 `INSERT OR IGNORE`를 유지합니다. `/상태`는 과거 처리 건수를 모두 집계하지 않고 기존 인덱스로 공통 분석 실패와 해당 서버의 전송 실패가 존재하는지만 확인합니다.

## 설치와 배포

Node.js 24 이상, Cloudflare 계정, Gemini API 키, Discord 앱과 서버 관리 권한이 필요합니다.

```sh
git clone https://github.com/hyxx-su/Tibo-bot.git
cd Tibo-bot
npm ci
cp wrangler.example.jsonc wrangler.local.jsonc
cp .dev.vars.example .dev.vars
npx wrangler login
npx wrangler d1 create tibo-bot-db
npx wrangler queues create tibo-bot-jobs
```

`wrangler.local.jsonc`에 자신의 Worker·D1·Queue 이름과 D1 ID를 넣습니다. Queue 생산자와 소비자 이름은 같아야 합니다. 실제 설정과 `.dev.vars`는 Git에서 제외됩니다.

| 변수 | 값 |
| --- | --- |
| `DISCORD_PUBLIC_KEY` | 앱 퍼블릭 키 |
| `DISCORD_APPLICATION_ID` | 앱 ID |
| `DISCORD_TEST_GUILD_ID` | 기존 단일 서버 채널·발송 이력 이관 대상 ID |
| `DISCORD_TEST_CHANNEL_ID` | 기존 초기 알림 채널의 대체값 |
| `DISCORD_NOTIFY_CHANNEL_ID` | 기존 서버의 초기 알림 채널. 이후 `/채널`의 저장값 우선 |
| `NITTER_BASE_URL` | 공개 미러 HTTPS 주소 |
| `WATCH_ENABLED` | 준비 후 문자열 `"true"`로 설정. 기본 `"false"` |
| `SITE_RESETS_ENABLED` | 사이트 리셋 감시. 기본 `"false"`, WATCH_ENABLED도 활성화 필요 |
| `RESET_ANALYSIS_DAILY_LIMIT` | 자동 분석 시도 일일 상한. 기본 100, 최대 100 |

비밀값은 `.dev.vars`에 로컬 개발용으로 저장하고 배포 환경에는 암호화 비밀변수로 등록합니다. **자동 발신에 봇 토큰이 필요합니다.**

```sh
npx wrangler secret put GEMINI_API_KEY --config wrangler.local.jsonc
npx wrangler secret put DISCORD_BOT_TOKEN --config wrangler.local.jsonc
npx wrangler d1 migrations apply tibo-bot-db --remote --config wrangler.local.jsonc
```

CLI에 D1 관리 권한이 없으면 해당 데이터베이스 Console에서 `migrations/0001_watch.sql`, `0002_thread_context.sql`, `0003_guild_channels.sql`, `0004_site_resets.sql`을 순서대로 실행할 수 있습니다. 기존 설치에는 아직 적용하지 않은 파일만 실행합니다. 두 번째 파일은 열을 추가하므로 최초 한 번만 적용합니다. 기존 기준점·글 이력은 유지합니다. **새 코드를 배포하기 전에 0003을, 사이트 감시를 활성화하기 전에 0004의 테이블·인덱스를 적용해야 합니다.**

Discord 앱을 `bot`, `applications.commands` 스코프와 채널 보기·메시지 보내기·링크 임베드·애플리케이션 명령어 사용 권한으로 설치합니다. `WATCH_ENABLED`를 `"true"`로 바꾼 뒤 배포합니다.

```sh
npm run deploy
npm run register:command -- --application-id YOUR_APP_ID --global
```

명령 등록에는 `.dev.vars`의 봇 토큰을 사용합니다. 자동화에서는 `DISCORD_BOT_TOKEN_FILE`로 보호된 파일을 지정하고 `node scripts/register-command.mjs ...`를 실행할 수도 있습니다. 지정한 서버 또는 `--global` 범위의 `/상태`·`/채널`을 생성·갱신합니다. 기존 `/알림설정`만 있으면 명령 ID를 유지해 `/채널`로 이름을 바꿉니다. `/채널`이 이미 있으면 이를 먼저 갱신한 뒤 같은 범위에 남아 있는 `/알림설정`·`/검증`만 개별 삭제합니다. 다른 이름의 명령은 건드리지 않습니다.

운영 봇은 전역 명령만 등록합니다. 서버별로 다시 등록할 필요가 없습니다. 개발용 서버에만 명령을 등록하려면 위 전역 등록 대신 `--guild-id YOUR_GUILD_ID`를 사용하세요. 같은 앱·이름의 명령을 전역과 서버 범위에 모두 등록하면 중복으로 표시될 수 있습니다. 개발에서 운영으로 전환할 때는 전역 명령이 생성된 것을 확인한 뒤 기존 서버 전용 `/상태`·`/채널`을 해당 명령 ID로 개별 삭제합니다. 전역 등록 스크립트는 다른 범위의 명령을 자동으로 삭제하지 않습니다.

Discord 개발자 포털의 Interactions Endpoint URL을 아래 형태로 설정합니다. 실제 서명 확인 요청이 통과해야 저장됩니다.

```text
https://YOUR_WORKER.YOUR_SUBDOMAIN.workers.dev/discord
```

Cron은 `* * * * *`로 매분 실행됩니다. [예약 변경 전파에는 최대 15분이 걸릴 수 있습니다.](https://developers.cloudflare.com/workers/configuration/cron-triggers/) `/상태`에서 기준점과 마지막 수집 성공 시각을 확인하세요. 첫 기준점 저장 전에는 감시가 시작된 것으로 간주하지 않습니다.

## 운영과 제한

- **중지·재개:** `WATCH_ENABLED`를 `"false"`로 바꾸고 재배포합니다. 예약 자체도 없애려면 `triggers.crons`를 `[]`로 바꿉니다. 재개할 때는 기존 D1 이력을 유지합니다.
- **수집 범위:** 새 게시글·답글 대상이며 재게시, 다른 작성자의 문맥, 최초 기준점 이전 이력은 제외합니다. 최대 3페이지까지 따라갑니다. 기준점 이후에 작성됐지만 미러에 늦게 노출된 글도 조회 페이지 안에 있으면 발견합니다.
- **무료 미러:** 차단·429·HTML 변경·갱신 지연·오래된 캐시가 생길 수 있습니다. 다음 주기에 다시 시도하지만 전체 글 무누락은 보장하지 않습니다. 마지막 성공 시각은 미러 응답을 받은 시각이며 X 최신성 보증이 아닙니다.
- **중복 방지:** 글 ID, 처리 단계, 작업 점유와 Discord nonce를 사용합니다. 발송 성공 직후 저장에 실패하고 장시간 후 재시도하는 경우까지 정확히 한 번 전송을 보장하지 않습니다. [Discord nonce 중복 검사는 최근 몇 분 범위입니다.](https://docs.discord.com/developers/resources/message#create-message)
- **실패 처리:** 발송·분석은 최대 6회, 간격을 늘려 재시도합니다. 인증·권한 오류는 즉시 실패로 남깁니다. `/상태`에 오류 안내가 표시되면 운영자가 토큰·권한·서비스 상태를 확인하고 해당 작업을 재개해야 합니다.
- **AI와 시간:** 분류 오류 가능성이 있습니다. 현재 글과 미러에 표시된 동일 스레드의 앞선 동일 작성자 글 최대 5개를 함께 읽습니다. 다른 작성자나 단순히 인접한 글은 합치지 않습니다. 키워드 없는 암시적 글도 분석하지만 직접 연결된 근거가 없으면 초기화로 확정하지 않습니다. ISO 날짜·시간대, 명시된 날짜/오늘/내일과 UTC·KST·PT·ET·PST·PDT·EST·EDT, 분·시간 후, `by/before/at midnight 시간대` 표현을 지원합니다. `by/before`는 정확한 실행 시각이 아니라 “까지”라는 기한으로 표시합니다. 주중 이름·시간 범위 등 미지원 표현이나 날짜·시간대 누락은 확정하지 않습니다. 원문에 없는 다음 초기화 시각은 예측하지 않습니다.
- **분석 상한:** 자동 분석 시도는 UTC 날짜 기준 최대 100회입니다. 상한 도달 시 미분석 글은 일반 글·미디어 답글을 포함해 다음 UTC 날짜(한국시간 오전 9시)까지 분석과 발송을 기다립니다. 이미 분석을 마친 글의 발송은 계속됩니다. 재시도도 분석 시도 횟수에 포함됩니다. 이 상한은 실제 잔여 무료량을 조회하는 기능은 아닙니다.
- **무료 사용량:** 매분 X 수집 Queue만 정상 처리해도 하루 약 4,320회 연산을 사용합니다. 사이트 감시도 켜면 수집 작업 두 종류만으로 하루 약 8,640회이며 새 글·분석·발송·재시도는 추가됩니다. 사이트 감시는 Gemini 분석 횟수를 사용하지 않습니다. [Queues](https://developers.cloudflare.com/queues/platform/pricing/), [Workers](https://developers.cloudflare.com/workers/platform/limits/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [Gemini](https://ai.google.dev/gemini-api/docs/rate-limits)의 한도를 계정에서 확인하세요. 유료 요금제로 자동 전환하도록 설정하지 않습니다.

## 관리자 단건 재검증

감시 기준점 이전의 특정 글을 검증할 때는 Cloudflare Queues 관리 화면 또는 인증된 API로 `{"kind":"watch-replay","postId":"실제_글_ID"}` JSON을 보낼 수 있습니다. 현재 미러 첫 페이지에서 해당 글을 다시 읽으며, 지정하지 않은 과거 글은 발송하지 않습니다. 이미 완료된 이력은 덮어쓰지 않습니다. 이 작업은 공개 HTTP 요청이나 일반 Discord 명령으로 노출되지 않습니다.

## 개발과 검증

```sh
npx wrangler d1 migrations apply tibo-bot-db --local --config wrangler.local.jsonc
npm run dev
npm test
```

`npm test`는 배포 없는 빌드 후 전체 회귀 테스트를 실행합니다. 실제 계정·키·게시글을 사용하지 않으며 외부 API는 합성 응답으로 대체합니다. 기준점, 링크 단독 발송, 시간 변환과 DST, 중복 작업, 429 재시도, 장애 중 작업 복구, 분석 상한, 여러 페이지 수집, Discord 서명, 다양한 한국어 질문과 날짜 해석, 재질문 구분, 즉시 응답과 실패 복구를 검증합니다.

선택적으로 `GEMINI_API_KEY` 환경변수를 안전하게 설정한 터미널에서 `node scripts/evaluate-reset-analysis.mjs`를 실행하면 실제 Gemini로 합성 사례 22개를 분류합니다. API 사용량을 소비하며 Discord 발송이나 운영 DB 변경은 하지 않습니다. 키워드 없는 완료, 짧은 답변의 문맥 유무, 일반 배포, 오탈자, 초기화권 지급, 부분 반영, 부정, 빈 본문, 외부 지시문과 과거 회상·인용 감사·취소·기한 수정·일부 플랜 완료를 검증합니다. 사례 이름을 인자로 주면 해당 사례만 실행하며, HTTP 429가 발생하면 남은 호출을 중단합니다. 한 번의 통과가 모든 미래 게시글의 정확성을 보장하지는 않습니다.

실제 서비스 실행 기록과 한계는 [검증 기록](docs/verification.md)에 정리합니다.


## 온라인 표시 설정

배포 설정의 `durable_objects`와 SQLite 마이그레이션 이력을 유지하고 `GATEWAY_ENABLED`를 `"true"`로 설정합니다. 기존 `DISCORD_BOT_TOKEN`을 사용합니다. 기본 모드는 입장·퇴장 감지를 위한 비특권 `GUILDS` intent만 사용합니다. 일반 채팅 질문을 사용하려면 Discord Developer Portal의 Bot 설정에서 **Message Content Intent**를 허용하고 `RESET_CHAT_ENABLED="true"`로 배포합니다. 이때 `GUILD_MESSAGES`·`MESSAGE_CONTENT`도 요청합니다. 권한 설정을 바꾼 뒤에는 새 Gateway 연결에 반영되어야 합니다. 배포 후 다음 Cron 실행에서 연결을 시작합니다. 공개 `/health`는 최소 서비스 상태만 반환하며 내부 객체를 호출하지 않습니다. 실제 온라인 연결 상태는 Discord의 비공개 `/상태`로 확인합니다.

연결 객체 이름은 고정되어 한 개만 사용합니다. Heartbeat ACK 누락, 연결 종료, Discord의 재접속 요청을 처리합니다. 살아 있는 세션은 재개하고, 새 인증은 재시작을 포함해 최소 2분 간격으로 제한합니다. 토큰의 SHA-256 해시로 교체를 구분하여 새 토큰에는 이전 인증 오류의 한 시간 대기를 적용하지 않습니다. 동일 토큰으로 재배포할 때는 대기가 유지됩니다. Gateway 저장소에는 토큰 원문을 저장하지 않습니다. 복구 대기는 최대 15분이며 치명적인 인증·설정 오류는 한 시간 동안 재시도를 제한합니다. `GATEWAY_ENABLED="false"`로 재배포하면 다음 Cron에서 연결을 종료합니다. 배포 설정에서 Durable Object 마이그레이션 이력을 임의로 삭제하지 마세요.

[Cloudflare 공식 요금표](https://developers.cloudflare.com/durable-objects/platform/pricing/) 기준 Workers Free의 Durable Objects 실행 시간은 하루 13,000 GB-s입니다. 외부 WebSocket은 hibernation 대상이 아니므로 연결 중 실행 시간을 소비합니다. 객체 하나의 24시간 연결은 대략 11,000 GB-s로 무료 한도 안에 들어가는 계산이지만 계정의 다른 Durable Objects 사용량도 합산됩니다. 무료 한도 초과 시 해당 작업은 오류로 중단되며, 장애나 배포 중 일시적인 오프라인 표시는 발생할 수 있습니다.


## 보안 운영

- Discord 요청은 Ed25519 서명과 ±5분 유효 시간을 확인합니다. 알림 채널 설정은 서버 관리·관리자 권한과 봇의 채널 권한을 확인합니다. 제거한 `/검증` 요청은 새 수집·분석 작업을 만들지 않습니다.
- 기존 `COMMAND_GUARD` Durable Object 바인딩·마이그레이션 이력은 유지합니다. 일반 채팅 질문은 별도 `discord-reset-chat` 객체에 식별자·제한 시각만 저장하여 중복과 호출량을 제한합니다. 과거 검증 명령의 예산과 분리하며 새 검증 명령은 제공하지 않습니다. 제거 전에 이미 큐에 저장된 검증 작업은 기존 만료·재시도 제한 안에서 마무리합니다.
- 수집원은 현재 확인한 `https://x.noodl3.net`만 허용합니다. 다른 미러를 쓰려면 수집기의 허용 목록도 검토해야 합니다. 외부 HTTP 리다이렉트는 자동 추적하지 않습니다.
- Discord 입력은 64 KiB, 미러 HTML은 2 MiB, Gemini 응답은 64 KiB로 제한합니다. AI 요약의 외부 링크를 제거하고 Discord 서식을 이스케이프하며, 멘션은 비활성화합니다.
- `sharp`와 `undici`의 보안 패치는 `overrides`로 고정합니다. 개발 도구에 필요한 패치이며 Worker 런타임에 해당 Node 패키지를 포함하는 것은 아닙니다. 의존성 변경 후 `npm test`와 `npm audit`를 실행합니다.
- 키·봇 토큰·개인별 배포 설정은 Git에 넣지 않습니다. 채팅이나 로그에 노출된 자격 증명은 발급처에서 폐기·재발급하고 Cloudflare secret도 교체해야 합니다.

자세한 점검 범위와 한계는 [보안 점검 기록](docs/security-review.md)을 확인하세요.
