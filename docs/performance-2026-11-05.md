## 개선 전 운영 속도

11월 5일 18:03 KST 측정. 11월 1일 이후 저장 이력과 서버별 최근 메시지 100개를 대조하여 25개 게시글의 최초 확인 가능한 서버 전달을 집계했다. 게시 시각은 분 단위로 오차가 있고, 당시 미완료 1건은 지연 분포에서 빠져 있다.

| 구간 | p50 | p95 |
| --- | --- | --- |
| 게시 → 발견 | 46.0초 | 106.1초 |
| 발견 → Discord 도착 | 16.6초 | 약 26.1분 |
| 게시 → Discord 도착 | 68.9초 | 약 26.9분 |

정상 처리 19건은 60초 이내였고, 나머지 6건이 긴 꼬리 지연을 만들었다. 이번 변경의 주된 목표는 정상 경로의 불필요한 Queue 대기를 줄이고, 분석 장애 때문에 원문 링크까지 수십 분 누락되는 문제를 해소하는 것이다.

이전 채팅 응답의 초기 실측 예는 4.579초와 0.816초였다. 최근 조회 가능한 10월 28일 7개 채팅 표본은 p50 0.544초, 최댓값 0.855초다. 같은 조건의 비교나 11월 5일 새 채팅 실측이 아니므로 배수 개선으로 해석하지 않는다. 일반 채팅은 저장된 분석을 재사용하며 이번에 모델 호출이나 새 캐시를 추가하지 않았다.

## 판별과 요약 개선

- 상태·유형·한국시간 변환·제목·요약을 한 Gemini 요청에서 처리하는 기존 구조를 유지했다.
- 제목과 요약의 원문 근거 구절을 함께 받으며 입력에 없는 구절은 거부한다. 작성자별 근거 경계, 정기/저장형 구분, 예정/진행/완료/언급/무관 구분을 유지한다.
- JSON·스키마·제목·요약·유형·원문 근거·완료 모순·HTTP 오류·타임아웃을 구분한다. 검증 실패는 한 번만 재검토하며 HTTP 오류 본문이나 이전 모델 출력은 재주입하지 않는다.
- 프롬프트에 사용한 회귀 자료 32개와 별도 평가 자료 12개를 분리했다. 평가 도구는 상태 혼동 행렬, 관련 여부 precision/recall, 유형·시각 일치, 호출 실패율과 응답 지연을 출력한다.
- 프롬프트 개선은 재학습이 아니다. 근거 구절의 일치도 완전한 의미 검증이 아니며, 무료 미러의 누락이나 보지 못한 미디어 내용을 복구하지 않는다.

실제 평가에서 외부 Gemini 503이 반복됐다. 첫 회귀 실행은 12건 중 5건이 정상 응답·검증 통과, 7건이 503이었다. 별도 평가 12개 중 4개를 시도한 뒤 연속 실패로 중단했다. 1개 통과, 원문 근거 검증 실패 1개, 503 2개였다. 근거 검증에 실패한 합성 사례는 내부 오류 코드로 재검토하여 올바른 일반 글 분석을 받았다. 성공 요청 중 약 3.6초와 38.2초가 관찰됐다. 이 표본으로 운영 정확도 향상이나 낮은 p95를 확정할 수 없다.

## 검증 결과와 운영 관찰

- 배포 전 빌드 및 738개 자동 테스트 통과. 테스트는 합성 데이터와 외부 API 모의 응답을 사용한다.
- 1차 배포 버전 `a45e5f48-2cdf-4075-a442-212f75c249b1`의 Cron 수집 2회 정상, 예외 없음. 관찰된 CPU 시간은 50·55ms였다.
- 관리자 재검토 호환 보완 후 최종 배포 버전은 `cfc3c2b0-58be-43de-b69f-15f0aa1df2d1`이며 health 응답이 정상이다.
- 구형 재시도로 대기하던 1건을 재개했다. Gemini 503을 확인한 뒤 원문 링크를 4개 서버에 전달했다. 해당 Discord 요청은 406~473ms, 소비 작업 CPU는 3~5ms였다. 이 게시글은 과거 대기 시간이 누적돼 새 버전의 발견→발송 비교 표본으로 쓰지 않는다.
- 복구 후 운영 DB에서 게시글 미완료 0건, 전달 미완료 0건을 확인했다. 단, 분석 최종 실패 1건은 unavailable로 남고 링크만 전달됐다.
- 실제 분석 완료 지연을 기록하는 `analysis_ms`, 발견부터 분석까지의 시간, Discord 요청 시간과 발견부터 전달까지의 로그를 추가했다. 오류 본문·키·질문 내용은 기록하지 않는다.
- `npm audit --omit=dev` 결과 운영 의존성 취약점 0건. 이 결과는 전체 코드 보안 무결성을 의미하지 않는다.

정상 새 글의 발견→도착 목표는 3~10초다. 이는 측정 완료 수치가 아닌 목표이며 Gemini·Queue·Discord 응답 상태에 따라 더 길어질 수 있다. 게시→발견에는 여전히 1분 수집 주기와 미러 갱신 지연이 있다. 서비스 오류가 안정된 뒤 독립 평가와 신규 게시글 지연 표본을 다시 모아야 개선 폭을 확정할 수 있다.

## 배포·복구

DB 스키마와 기준점·발송 이력을 바꾸지 않았다. 정상 처리 단계는 저장 후 다시 claim하므로 중간에 작업이 종료돼도 Cron이 재개한다. 링크 전송 중 내용이 갱신되면 먼저 전송한 메시지 ID를 보존하고 pending으로 남겨 새 내용을 PATCH한다. 발송 성공 직후 DB 저장 실패가 장시간 지속되는 상황까지 exactly-once 전송을 보장하지는 않는다.

분석 오류 복구 기준은 [Gemini API 오류 문서](https://ai.google.dev/gemini-api/docs/api-errors)를, Queue 지연 상한은 [Cloudflare Queues 제한](https://developers.cloudflare.com/queues/platform/limits/)을 참고했다. 유료 전환이나 계정·권한 변경은 하지 않았다.
