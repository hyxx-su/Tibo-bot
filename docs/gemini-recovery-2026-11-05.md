# 2026-11-05 Gemini 장애와 링크 전용 알림 복구

## 확인된 원인

같은 키로 모델 목록·단순 요청은 성공했지만, 3.5 Flash-Lite 분석 요청에서 HTTP 503, `UNAVAILABLE`, 제공자 과부하 안내를 확인했다. 3.5의 온도·추론 설정을 바꾼 분석 진단 10회에서는 200 2회, 503 7회, 45초 타임아웃 1회였다. 추론 수준을 낮추는 것만으로 장애가 해소되지 않았다. 이 수치는 서로 다른 설정을 시험한 소규모 진단이며 일반적인 장애율이나 통제된 성능 비교가 아니다.

대체 모델 3.1 Flash-Lite에서도 장시간 평가 중 타임아웃·503이 관찰됐다. 503은 봇이 제거할 수 있는 오류가 아니므로 모델 선택과 재시도·기존 메시지 복구를 함께 적용했다. 별도로 빠르게 연속 평가했을 때 429가 발생했으며, 이후 평가는 호출 사이 7초를 두고 진행했다. 429와 503을 같은 원인으로 취급하지 않는다.

## 적용 범위

- 게시글 분석의 기본 모델을 `gemini-3.1-flash-lite`로 변경했다. `RESET_ANALYSIS_MODEL`에는 검증한 3.1·3.5 Flash-Lite만 허용하며 temperature는 모델 기본값, 추론은 MEDIUM을 사용한다.
- 요약 배열과 근거 배열을 따로 생성하면 개수가 어긋나 정상 내용도 거부됐다. 생성 응답을 `{text, evidence}` 쌍으로 받고 원문과 대조한 뒤 기존 저장 필드로 변환한다. 저장 스키마와 Discord 표시 형식은 유지했다.
- 일부 플랜 완료·나머지 미확인이라는 원문을 전체 완료로 분류하면 거부하고 재검토한다. 한도 상향·타인의 주장에 대한 출처 질문·농담 속 직접적인 초기화 언급의 판별 지침을 보완했다.
- “Might be” 같은 유보 표현을 확정적인 동의로 요약하지 않도록 제목·요약 지침을 보완했다.
- 408·500·502·503·504·타임아웃·네트워크 오류는 총 6회까지 시도한다. 재시도 대기는 15·60·180·900·3,600초이며 더 긴 Retry-After는 우선한다. 처음 세 대기는 유지하고 15분·1시간의 지연 복구 기회를 추가한 것이다.
- 검증 실패는 최대 2회, 요청 제한 등 그 밖의 재시도 가능 오류는 최대 4회다. 인증·영구 오류는 반복하지 않는다. 운영의 일일 분석 예산 100회, 작업 claim, 기존 메시지 ID와 발송 이력은 유지한다.
- 첫 실패 때 원문 링크를 전달하고 분석이 복구되면 동일 메시지를 PATCH한다. 6회 모두 실패하면 링크만 남을 수 있으므로 영구적인 성공을 보장하는 정책은 아니다.

## 검증 과정

자동 테스트 750개와 Wrangler 빌드를 통과했다. 네 번째 서버 장애 뒤에도 작업을 유지하고, 나중에 분석이 성공하면 신규 POST 없이 기존 메시지에 PATCH하는 통합 테스트를 포함한다.

실제 API 평가에서 발견한 오분류를 숨기지 않고 수정 단계를 나눴다.

1. 요약·근거 쌍 적용 후 일부 플랜만 완료된 사례의 전체 완료 오판을 발견하여 원문 범위 검사를 추가했다.
2. 다음 회귀 32건은 통과했지만 별도 합성 평가에서 한도 상향·타인의 주장에 대한 질문을 관련 언급으로 오판한 2건을 발견했다. 개선에 사용한 두 사례는 회귀 자료로 이동하고 별도 표현을 추가했다.
3. 실제 원문 24건 평가에서는 23건이 통과했다. 농담 속 초기화 요구 언급 1건을 일반 글로 놓쳐 지침을 보완했다. 이 평가의 분석 p50은 3.122초, p95는 22.616초였고 근거 검증 실패 1건은 재검토로 복구했다.
4. 이 단계에서 오류 사례 재확인 4건, 새 표현 2건, 저장형 지급 완료·진행 사례 2건은 모두 통과했다. 이는 서로 목적이 다른 표본이며 합쳐서 운영 정확도로 표현하지 않는다.

최종 배포 후보의 실제 원문 재평가·운영 확인 결과는 아래와 같다. 실제 수집 원문, API 키, 서버·메시지 식별자, 개별 원본 보고서는 비공개 보관한다. 모델 출력으로 정답을 생성하지 않았으며 모호한 정답 2건은 평가에서 제외했다.

## 최종 배포 후보 실측

최종 분석 코드로 같은 실제 원문 24건과 추가 합성 회귀 1건을 재평가했다. 7초의 사례 간 대기는 분석 시간에 넣지 않았으며, 사례 내 재검토 대기는 별도 열에 포함했다.

| 항목 | 실제 원문 24건 결과 |
| --- | --- |
| 분류·지정된 시각 검증 일치 | 24/24 (재검토 포함) |
| 첫 요청에서 검증까지 통과 | 23/24 |
| 관련 여부 precision / recall | 16/16 / 16/16 |
| 상태별 일치 | 완료 3, 예정 6, 언급 7, 일반 8 |
| API 요청 | 25회, HTTP 오류 0회, 근거 검증 거부 1회 |
| 성공 분석 시간 p50 / p95 / 최대 | 2.344초 / 3.081초 / 3.211초 |
| 재검토 대기 포함 p50 / p95 / 최대 | 2.344초 / 3.211초 / 20.712초 |

추가 합성 회귀 1건도 첫 요청에서 통과했다. 합계 25건에 26회 요청을 사용했다. 전 단계의 같은 실제 원문 24건은 23/24, p50 3.122초·p95 22.616초였다. 외부 서비스 부하와 모델 출력 변동이 섞인 순차 측정이므로 이 차이를 코드 변경만의 속도 개선율로 주장하지 않는다. 앞선 평가에서는 3.1에서도 타임아웃·503이 발생했으므로 이번 묶음의 HTTP 오류 0회가 상시 무장애를 뜻하지 않는다.

수정 요청된 글은 원문과 연결 문맥을 확인하여 기존 서버 메시지 4개를 PATCH했고 모두 다시 조회해 검증했다. 신규 메시지는 만들지 않았다.

운영과 같은 `processWatchJob` → `processDeliveryJob` 코드를 격리된 로컬 D1·작업 실행기로 구동하고 실제 Gemini·Discord API를 호출하는 추가 검증도 수행했다. 분석 1.393초, Discord PATCH 및 저장 0.386초, 입력 등록부터 수정 저장까지 2.815초, Discord 재조회까지 3.149초였다. 기존 테스트 메시지 ID를 유지했고 완료 뒤에는 네 서버에 적용한 검토된 문구로 복원했다. 이 한 건은 Cloudflare Queue에서 새 게시글을 발견하는 전체 운영 지연 측정이 아니며 1분 수집 주기·미러 갱신 지연을 포함하지 않는다.

Cloudflare 배포 버전은 `c28e75bf-a38f-4973-a92b-2a4defcc9dce`다. 배포 후 health 200, 수집 성공 시각의 갱신, 수집 오류 없음, 게시글·전달 대기 0건, 수정된 전달 4건의 완료 상태를 확인했다. 55초 실시간 tail에서는 이벤트를 확보하지 못했으므로 새 버전의 CPU 시간이나 예외 0건을 tail 측정 결과로 주장하지 않는다. DB·기존 발송 이력은 보존했다.

## 제한과 롤백

실제 원문 평가는 저장된 자료에서 초기화 관련 16건과 일반 글 8건을 선택한 회귀 검증이다. X 전체 게시글이나 무작위 운영 표본이 아니며, 반복 평가·개선에 사용했으므로 미래 정확도를 보장하는 독립 시험으로 해석하지 않는다. 게시글 발견 지연·미러 누락·실제 사용자 계정의 적용 여부는 분석 시간과 별개다.

DB 스키마·수집 기준점·채널 설정은 바꾸지 않았다. `RESET_ANALYSIS_MODEL`로 기존 모델을 지정할 수 있지만 해당 모델의 현재 가용성을 먼저 확인해야 한다. 재시도 변경은 별도 커밋이므로 독립적으로 되돌릴 수 있다. 유료 전환이나 권한 추가는 하지 않았다.
